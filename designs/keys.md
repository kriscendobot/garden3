# Keys are files

The prior garden passes provider keys to the container as environment
variables. The garden takes the tower's way. Code: `src/keys.js`,
`keys/registry.yay`.

## What the priors do

**The prior garden** (`garden` launcher, `entrypoint.sh`,
`scripts/systemd/seed-api-key-handoff.sh`, `designs/secret-management.md`): six
provider keys are `docker run -e` flags, copied at boot into
`/run/environment.d/60-garden-api-keys.conf`, and so inherited by every unit
and every worker. A file store (`scripts/secrets/`, mode 0700, with a
registry) was added in November 2026 as a compatibility layer; removing the
`-e` path is described as a later release.

**The tower** (`scripts/jobs/set-api-key.sh`, `worker-auth.py`,
`scripts/typesafe/common.sh`, `divergence/image.md`): a key is one file under
`.tower-state/secrets/`, mode 0600 in a 0700 directory. It is written from the
terminal or a pipe, never from argv. A script that needs it reads the file,
refuses it if any group or other bit is set, and hands it to `curl` on stdin.
A worker's environment is stripped of every key variable and it gets its
credential through a helper the harness calls. One exception remains:
`ANTHROPIC_API_KEY` may still be passed with `-e`.

## The garden's rules

1. **No key in the environment, with no exception.** The launcher passes no
   key (`test/bootstrap.test.js` checks its `-e` flags). Dispatch builds a
   worker's environment from nothing and `scrub` removes every known key
   variable and anything named `*_API_KEY`, `*_TOKEN` or `*_SECRET`.
2. **A key is a file under the state directory**, `.garden-state/`, which is
   0700 and the steward's. Job accounts cannot read it at all (checked in the
   running box: a job's `ls` and `cat` there are refused), and nothing under
   it is ever part of a job's home.
3. **A registry** (`keys/registry.yay`, on the shed) names each key, what it is
   for, where it lives, and its one **consumer**. `read` is refused for any
   other consumer, and for a file whose mode is not exactly 0600.
4. **Jobs hold no GitHub credential.** Only the steward does.
5. **The model credential** (`anthropic-worker`) reaches the harness through
   the harness's own key helper, as in the tower. Not built yet.

## The bot's GitHub login

The operator logs the bot in **by hand**, inside `./garden sh`, with gh's own
login (`main:SETUP.md`, step 8):

```sh
gh auth login --hostname github.com --git-protocol ssh --web --scopes admin:public_key
```

There is no wrapper. What makes a plain login land in the right places is the
shell `./garden sh` opens:

| Thing | Where | Mode |
| --- | --- | --- |
| the steward's home, `$HOME` in the box (and its account's home) | `.garden-state/steward/` | 0700 |
| gh's store, holding the token (`GH_CONFIG_DIR`) | `.garden-state/steward/.config/gh/hosts.yml` | 0600, written by gh |
| the bot's ssh key, generated by gh in the box | `.garden-state/steward/.ssh/id_ed25519` | 0600, written by gh |
| github.com's host keys, pinned | `.garden-state/steward/.ssh/known_hosts` | written at each boot from `config/github-known-hosts` |
| ssh configuration: that key, those host keys, strict checking | `.garden-state/steward/.ssh/config` | 0600, written at each boot |
| the identity the steward commits as, in the box | `.garden-state/steward/.gitconfig` | `Kriscendo Bot`, from `config/garden.yay` |

- **Nothing lands in the checkout.** The steward's home used to be the
  checkout; it is now under the state directory, so gh and ssh-keygen cannot
  write a token or a private key into the working tree.
- **One source of truth for the token: gh's store.** The `github-bot` key is
  registered with `provider: gh`. The key module does not keep a copy: when
  the steward's GitHub client needs the token it runs `gh auth token` and
  reads it from a pipe, checks first that gh's store is 0600, and gives it to
  curl on standard input. `keys set github-bot` is refused. Logging the bot
  out with gh removes the key, because there is nothing else.
- **The ssh key** is registered as `github-ssh`, consumer `steward`, at the
  path above. It is generated in the box and never leaves it; only its public
  half goes to GitHub.
- **Host keys are pinned, not trusted on first use.** `config/github-known-hosts`
  holds the three keys GitHub publishes (their fingerprints are in the file and
  were checked with `ssh-keygen -lf` against GitHub's published ones); the ssh
  config sets `StrictHostKeyChecking yes`.
- **Identity.** In the box, the steward's commits are the bot's, from its own
  `.gitconfig`. The checkout's repository-local configuration is not touched,
  so on the host a maintainer commits as themselves, and the box never
  commits as the maintainer: it cannot see the host's git configuration.
  (The prior garden set the bot's identity in the checkout's own
  `.git/config`, which the host shared.)
- **`garden bot status`** is read-only: who gh says is logged in, whom ssh
  greets, the key's fingerprint, and whether modes are right. It performs no
  login.
- `ssh` and `ssh-keygen` are in the base image ([image.md](image.md)); `gh` is
  a capability a publishing host installs for itself.

## Status

Implemented and tested: set, modes, pattern, consumer, refusal of a loose
mode, status without values, the scrub; the token read through gh with a fake
gh; `keys set` reading standard input only; what the entrypoint lays down and
the read-only report, with a fake gh and ssh (`test/dispatch.test.js`,
`test/cli.test.js`, `test/login.test.js`, `test/watcher.test.js`). Checked in
the running box: the state directory and the steward's home are 0700, the
pinned `known_hosts` and ssh config are in place, gh 2.105.0 is installed,
`garden bot status` and `garden keys status` answer, and a job running as a
slot account cannot read any of it. **Not done and not verifiable here:** the
login itself, and anything against GitHub. Design only: the harness's key
helper, and the steward publishing branches and pull requests.

## Open questions

1. **Subscription logins.** The prior garden's workers mostly run on Claude
   subscription logins stored in the bind-mounted home, not API keys. Where
   does a login live when each job has a fresh home? Probably the steward's
   state, lent to the harness through the helper; this needs a real harness
   to settle.
2. **One bot token for everything the steward does**, or a narrower token per
   act (push to forks, comment, read)?
3. **Rotation.** The prior garden's registry has a maximum age per key and a
   watchdog. Not ported.
