# Yarn lock in its own commit

Purpose: every change to `yarn.lock` is its own commit, `chore: Update
yarn.lock`, after the `package.json` change that caused it, so that a rebase
can drop and regenerate it instead of merging it by hand.

Implementation and its tests stay together in the package's commit; only the
lockfile splits out.

## Procedure

```sh
git add packages/foo/package.json
git commit -m "feat(foo): add bar dependency"

npx corepack yarn install
git add yarn.lock
git commit -m "chore: Update yarn.lock"
```

The lockfile commit comes **after** the `package.json` commit, so dropping it
leaves a coherent state.

Without the network, `yarn install` can regenerate the lockfile only from
what the checkout already has. If it cannot, commit the `package.json`
change, leave the lockfile alone, and say in the report that it is owed.

## Pitfalls

- **`git commit --amend` drags a staged lockfile in.** Stage and commit it
  last, alone.
- **Combined by accident**: `git reset HEAD~1`, stage selectively, commit as
  two. A retcon applies the same split across a whole branch.
- **A rename changes the lockfile.** Renaming a workspace's directory or its
  `name` changes its key (`"@scope/<name>@workspace:packages/<dir>"`). Still
  its own commit, regenerated by `yarn install` after every rename is in
  place. Never hand-edit the key.

## Rebase recovery

A branch carrying a lockfile commit usually conflicts on it when rebased onto
a base that moved. Because it is its own commit, the recovery is mechanical:

```sh
git rebase <base>
# conflict on yarn.lock
git rebase --skip                 # drop the old lockfile commit
# finish the rebase; apply any review fixes on top
npx corepack yarn install         # regenerate against the new base
git add yarn.lock
git commit -m "chore: Update yarn.lock"
```

Skip only when the conflicted commit touches nothing but the lockfile. Any
other conflict is resolved by reading both sides, not skipped.
